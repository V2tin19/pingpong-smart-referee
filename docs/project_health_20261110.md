# 项目健康检查与 YOLO 部署优化（2026-11-10）

## 1. 接手结论

**结论：适合继续研发，不宜直接按当前文档宣称的硬件性能验收上线。**

- 优点：感知、轨迹、判罚、渲染分层清晰；核心不依赖深度学习框架；有可执行单测、两份免模型观测样例及真实模型/视频/标注。
- 基线：起始提交 `894b251`，原有 203 项 unittest 全通过。原有 [11 月 6 日汇报](../11.6pingpong.md) 是接手时已存在的未跟踪文件，本轮未修改。
- 覆盖缺口：新证据引擎原来只有 5 项测试，包含多个能反向计分的生命周期/事件语义缺陷；“单测全绿”不等于比赛判罚正确。
- 当前生产默认保持 `imgsz=960`、FP32、原来的默认权重和 shadow 模式。没有把实验候选自动写成默认部署参数。
- 本轮没有重新训练、删除历史脚本、安装全局依赖、导出 TensorRT/RKNN，也没有提交 Git。

| 同 frame_id 重推后漏检仍能取到旧候选 | 回放/重试时感知结果与候选不一致 | [适配器](../adapters/yolo_adapter.py) 每次推理先清当前候选 |

| 稀疏标签缺项当作无球帧 | 旧 FP / Precision 报告可能失真 | [旧权重对比工具](../tools/compare_weights_benchmark.py) 保留显式不可见标签、排除 UNKNOWN，修正 ROI 缩放及分母范围，拒绝不完整解码 |

同时增加显式 `--device` / `--half`，FP16 兼容旧版 `half=True` 与本机新版 `quantize=16` 接口；默认仍不开启。移除入口未用的导入，忽略 pytest 缓存。

## 3. 输入缩小实验：不是只改一个 imgsz 就能无损提速

### 3.1 方法和限制

工具：[benchmark_input_sizes.py](../tools/benchmark_input_sizes.py)。使用生产适配器，而非另写一套裁剪/坐标还原实现。

- 权重：[yolo11n_game1_best.pt](../weights/yolo11n_game1_best.pt)，SHA256 `fed1e7c9c67dffee2c4f82ade2e7a6411daa092feb81c6cd3838a55cdf08b1ee`。
- 环境：RTX 4060 Laptop GPU、Windows、Python 3.10.21、Torch 2.6.0+cu124、Ultralytics 8.4.176、OpenCV 5.0.0；复用本机既有 `pytorch` Conda 环境，默认 Python 是另一个 CPU 环境。
- 固定 conf=0.18、IoU=0.45、device=0、batch=1；每尺寸加载独立模型，10 次额外预热，冷启动与正式测量分开。
- 使用预设 ROI 裁剪原图，再由模型缩放输入；误差始终以 **1920×1080 原图像素**计量，不随输入尺寸放宽容差。
- 绿台：本地 [50 秒视频](../data/test_4_50s.mp4) 全 6002 帧范围内 **504 个有效球心 + 5 个不可见标注**。
- 蓝台：本地 [完整视频](../data/test_3.mp4) 全 7800 帧范围内 **798 个有效球心 + 7 个不可见标注**。这不同于历史汇报只截前段的 120 个球心，不能直接对比历史 99.17%。
- 未标注帧是 UNKNOWN，完全不参与准确率/虚警计算。负坐标是不可见/不可定位，**不是已人工确认的无球背景**；12 个不可见标注远不够评估真实部署虚警率。
- 检测评价用最高置信候选，不含轨迹时序关联、落台/击球/回合判罚；全标注评测不等于全片每帧都有人工作真值。
- 计时覆盖适配器推理和结果转换，**不含视频解码、裁判、HUD、编码、相机队列**。这是稀疏帧单次桌面测量，不是端到端实时性能，也没有多次重复/热稳定置信区间。

### 3.2 全部可用标注，FP32

| 输入 imgsz | 绿台 Recall@5px | 绿台 Recall@25px | 绿台均值 / P95 ms | 蓝台 Recall@5px | 蓝台 Recall@25px | 蓝台均值 / P95 ms |
|---|---:|---:|---:|---:|---:|---:|
| 960 基线 | 92.06% | 92.26% | 11.03 / 12.32 | 97.12% | 97.24% | 11.39 / 13.15 |
| 832 | 91.87% | 92.06% | 10.40 / 12.07 | 97.37% | 97.49% | 11.67 / 19.33 |
| 768 | 91.47% | 91.67% | 10.91 / 12.11 | 97.12% | 97.24% | 14.16 / 25.59 |
| 640 | 80.95% | 81.15% | 10.87 / 16.02 | 92.98% | 93.11% | 13.52 / 24.48 |
| 512 | 64.68% | 64.68% | 10.64 / 12.39 | 79.07% | 79.32% | 12.58 / 23.61 |

原始逐帧记录：[绿台 FP32](../output/input_size_test4_full.json)、[蓝台 FP32](../output/input_size_test3_full.json)。这些输出在 Git 忽略目录下；本报告保留关键数据和复现命令。

**结论：**

1. 640/512 明显不满足“精度不损失”。绿台从 960→640 的 Recall@25px 下降 **11.11 个百分点**，到 512 下降 **27.58 个百分点**。
2. 832 可保留为后续候选，但绿台 504 个正例里净少命中 1 帧；蓝台虽净多命中 2 帧，不可见标注检出从 2→4。它没有跨场景通过默认的零退化筛选，且本机蓝台并未测到稳定提速。
3. 更小的网络输入面积并没有转化为同比例的适配器提速。Python/预处理/后处理、设备负载和逐帧调用可能占显著比例，需用 profiler 在目标硬件定位；不能单凭理论 FLOPs 推断瓶颈。
4. 条件平均定位误差只在检出帧上计算；漏检变多或一个大误检被消除都可能让均值“变好”，必须同时看召回与逐帧差异。蓝台960的中心误差均值2.21px、RMSE41.17px受到一个大误检影响，并不意味着小尺寸普遍定位更准。
5. 最初 300 正例抽样一度显示 832 在绿台有提升，但全标注结论发生反转。**抽样只做冒烟，不能代替验收。**

### 3.3 FP16 独立实验

同样覆盖全部标注，未改原图或采集帧率：

| 配置 | 绿台 Recall@5px / @25px | 绿台均值 / P95 ms | 蓝台 Recall@5px / @25px | 蓝台均值 / P95 ms |
|---|---:|---:|---:|---:|
| 960 FP16 | 92.06% / 92.26% | 14.72 / 23.80 | 97.12% / 97.24% | 14.35 / 22.55 |
| 832 FP16 | 91.87% / 92.06% | 13.04 / 22.62 | 97.24% / 97.49% | 13.51 / 22.90 |

原始记录：[绿台 FP16](../output/input_size_test4_fp16.json)、[蓝台 FP16](../output/input_size_test3_fp16.json)。960 FP16 在这些标注上召回与 FP32 相同，但条件中心误差稍变（绿台0.860→0.876px，蓝台2.210→2.243px），并没有在本次桌面测量中提速。不能由一次分时实验推断“FP16必然更慢”；也不能按常识承诺一定提速。应在目标机固定功耗/负载后交错重复测试，尤其对比 TensorRT 后端。

四组实验的配置、模型哈希、环境、完整指标及相对于同精度960基线的逐帧得失，归档在可纳入版本的 [精简机器可读证据](input_size_summary_20261110.json)。例如 FP32 960→832 在绿台 @5px **丢7帧、补6帧**，蓝台 **丢7帧、补9帧**；净召回持平或略升不代表关键帧没丢，仍需回合级验收。

### 3.4 复现

在装有 CUDA 视觉依赖的环境中：

```powershell
python tools/benchmark_input_sizes.py --video data/test_4_50s.mp4 --annotations data/test_4.zip --weights weights/yolo11n_game1_best.pt --preset test4 --sizes 960 832 768 640 512 --device 0 --output output/input_size_test4_full.json
python tools/benchmark_input_sizes.py --video data/test_3.mp4 --annotations data/test_3.zip --weights weights/yolo11n_game1_best.pt --preset test3 --sizes 960 832 768 640 512 --device 0 --output output/input_size_test3_full.json
```

可加 `--sample-count 300` 快速冒烟；正式不要加。`--half` 单独跑一轮，避免把缩图与精度格式两种因素混在一起。

工具的自动筛选默认要求 Recall@5/10/25px 不降、条件中心误差不增、不可见标注检出不增；即使通过，也只是该样本上的观察结果，不是统计等效或比赛判罚正确性承诺。

## 4. 尚未完成的部署与冗余风险

| 项目 | 判断与下一步 |
|---|---|
| 实时相机/RTSP | 入口先检查本地文件存在、依赖总帧数，并不支持设备号和直播流。已纠正帮助文字；下一阶段要做采集队列、硬件时间戳、背压/丢帧策略和长期运行，不应简单取消文件检查就宣称完成 |
| GPIO/UART/实体改分 | [硬件文档](hardware_interface.md) 是接口约定，不是驱动实现。直接 `points['A'] += 1` 示例不会完整同步轮转/终局/审计，应建设受控改分 API 和队列串行消费，不能多线程直接修改状态 |
| 证据引擎仍会自动落地低置信判罚 | 现有 shadow 模式只对照、不替代 legacy HUD；保留为研发对照。低置信自动加分、缺少发球击球证据等属于明确策略，需要带人工回合真值验收后再切 evidence |
| 片尾未结回合 | 当前没有在 EOF 后凭空推进未来时间。本轮不强制 tick(+timeout)，避免截断片段被虚构成“无人回击”；应输出 pending 状态/显式离线 flush 策略 |
| JSONL 与在线视频不等价 | JSONL 只保存顶层球观测，不包含带外多候选，重放可能与在线关联不同。不能把 JSONL 回放比分当作生产视频路径的逐帧完全等价证据 |
| 异常资源回收 | 视频主循环缺少完整的 try/finally，部分异常下 writer/适配器/文件可能未立即关闭；长期部署前需加强，并检查 writer.isOpened、准确统计实际处理帧数 |
| 非1080p HUD | 轨迹/落点是原始输入尺寸坐标，而 HUD 缩放以标定基准计算，需专项验证非1920×1080输入与渲染缩放组合；本轮尺寸实验只改模型输入，不改相机原图 |
| 旧单体脚本约990行 | [旧实现](../yolo_core/scripts/smart_referee_yolo.py) 重复跟踪、事件和渲染功能，生产不应再从这里扩功能。但几何和历史回归仍引用它作来源，本轮保留，建议后续独立标记 legacy/归档，不盲删 |
| 证据引擎未消费字段 | `serve_compliance`、`server_inferred`、`cross_dir` 有未消费状态/局部值；不在本轮安全修复中破坏潜在接口。下一轮应确认是未实现的规则还是可移除冗余，并补契约测试 |
| 训练负样本和泄漏 | 训练构建器按标注间隔抽取未标注背景，不能保证真无球；仍需人工复核。按帧随机拆背景也可能存在场景相关，后续按视频/回合隔离验证 |
| 依赖复现 | requirements 仅下限未锁版本；默认 Python 的 Torch 为CPU且无Ultralytics，与已有pytorch环境不同。报告记录实测环境；后续按目标平台建立锁定环境，不能直接以“已装 torch”判断使用GPU |

撤下 [硬件文档](hardware_interface.md) 中无实测记录的 RK3588/Orin/x86 FPS、内存和功耗承诺；未把本机测量外推给这些平台。

## 5. 下一步改进顺序与验收

1. **先确定部署约束**：设备/CPU/GPU/NPU、系统和驱动、当前模型/后端、实际输入张量、精度、相机分辨率/帧率、当前端到端 FPS 与 P95、目标延迟，以及“不损精度”是否允许统计波动。
2. **优先保持960做后端优化**：先对比 FP32/FP16，再评估固定形状 batch=1 TensorRT（NVIDIA）或设备对应后端。INT8 必须有小球难例校准与独立精度验收，不能宣称无损。
3. **832 保留备选，不立即启用**：补硬件现场视频、弱光/拖影/远台小球、发球/落台/遮挡前后难例。允许的召回、定位和回合误判变化应先定标准。
4. **保留采集原图，不先降采集帧率**：`imgsz`、相机分辨率、感知帧率、HUD/编码帧率是四个不同开关。只降 HUD 成本不影响感知时序；降感知帧率会直接影响反折/落台事件。
5. **必要时再训练**：如果目标硬件必须640，可做小尺寸/多尺度微调和难例补充，再用独立视频比较，不要只在训练集调阈值找“无损”。ROI也不能缩到漏掉台外击球/高球，动态ROI需全局重捕回退。
6. **最终按业务验收**：连续录像回放，比较球心召回、Recall@5px、人工确认无球FP、落台/击球事件F1、错误加分与漏判回合；再做目标设备长时间热稳定、队列延迟与丢帧测试。检测指标持平不代表裁判判分持平。
