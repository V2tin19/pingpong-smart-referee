# TTNet、TrackNet、YOLO 共用计分状态机方案

**不需要分别写三套计分状态机。建议三个模型共用一套状态机，各写一个适配器，把输出转换成统一格式。**

模型负责“看到了什么”，状态机负责“根据这些事件应该给谁加分”。更换检测模型时，乒乓球规则不会变化。

## 1. 推荐架构

```text
YOLO ─────适配器──┐
TrackNet ─适配器──┼→ 轨迹/事件处理 → 共用计分状态机 → 比分
TTNet ────适配器──┘                       ↑
                                语音纠错/实体按键
```

三个模型的差异主要在适配层：

| 模型 | 常见输出 | 适配层需要处理 |
|---|---|---|
| YOLO | 球框、置信度 | 提取球中心，关联连续帧 |
| TrackNet | 球位置热图 | 提取球中心，判断球是否可见 |
| TTNet | 球位置、落台/擦网事件，部分实现含分割 | 坐标还原、事件阈值与重复事件合并 |

具体字段以实际部署的实现为准。

## 2. 统一模型输出

统一后的数据可以是：

```python
observation = {
    "timestamp": 12.350,       # 视频时间，单位秒
    "ball_xy": (850, 420),    # 还原到原始图像坐标
    "ball_visible": True,
    "ball_confidence": 0.92,
    "bounce_score": None,     # 没有该输出的模型填 None
    "net_hit_score": None,
}
```

由中间的“轨迹/事件处理层”生成状态机真正需要的事件：

```python
event = {
    "timestamp": 12.350,
    "type": "BOUNCE",         # 落台、击球、擦网等
    "side": "A",
    "confidence": 0.90,
}
```

## 3. 分开事件提取，共用计分规则

**需要分开的是事件提取逻辑，而不是计分规则。**

- YOLO、TrackNet：主要根据连续轨迹推断落台、过网等事件。
- TTNet：可以直接利用事件输出，再结合轨迹和球台几何进行验证。
- 三者最终都输出统一的事件，交给同一个状态机。

共用状态机可以先设置：

```text
等待发球 → 发球进行中 → 对打中 → 回合结束候选 → 确认得分
                                   └→ 无法判断，等待人工确认
```

## 4. 实现注意事项

1. **使用时间戳，不使用固定帧数作为超时条件。** 三个模型处理速度、连续帧输入和输出延迟不同。
2. **不要把“球消失”直接当作失分。** 漏检、遮挡和飞出画面都可能导致球消失，需要结合之前的落台与击球事件判断。
3. **如果三个模型同时运行，要先融合、去重，再送入状态机。** 同一次落台只能产生一个事件；模型之间出现冲突时进入待确认，不能各加一次分。不同模型的置信度也不能直接取最大值。

## 5. 单目落点判断的限制

**单目摄像头不能把空中球的位置直接通过桌面透视矩阵转换成真实落点。**

透视变换只适用于桌面平面；应先通过时间序列判断落台时刻，再定位落点，否则会把空中球误判为出界。

## 6. 当前部署建议

采用：**三个独立适配器 + 一套统一事件接口 + 一套计分状态机**。

用同一段视频分别测试三个模型，可以直接比较最终判分准确率。

## 7. 适配器输出接口详细设计

**适配器应输出“统一的逐帧观测数据”，不要直接输出“谁得分”。** YOLO、TrackNet、TTNet 都转换成相同的数据结构，再交给轨迹与事件处理层。本节细化第 2 节的简化示例，实际实现建议统一采用本节字段命名。

### 7.1 统一逐帧观测 Observation

```python
observation = {
    # 帧身份与时间
    "frame_id": 1234,
    "timestamp_s": 20.567,       # 被预测帧的视频时间，不是推理完成时间
    "source": "yolo",           # yolo / tracknet / ttnet
    "image_size": [1920, 1080], # 原始图像宽、高

    # 球的观测
    "ball": {
        "visible": True,
        "center_px": [850.0, 420.0],
        "bbox_xyxy": [844, 414, 856, 426],  # 无检测框时填 None
        "confidence": 0.92,     # 模型原始分数；无可靠分数时填 None
    },

    # 模型自带的事件预测；没有这项能力时填 None
    "event_scores": {
        "bounce": None,
        "net_hit": None,
    },
}
```

坐标统一还原到原始图像坐标：左上角为原点，向右为 x 正方向，向下为 y 正方向。适配器负责撤销缩放、裁剪和 letterbox 补边，后面的模块不需要知道模型输入尺寸。

### 7.2 三个模型的字段映射

| 统一字段 | YOLO | TrackNet | TTNet |
|---|---|---|---|
| `center_px` | 检测框中心 | 热图峰值或连通域中心 | 球位置输出 |
| `bbox_xyxy` | 检测框 | 通常为 `None` | 没有框则为 `None` |
| `confidence` | 检测置信度 | 热图分数，需明确计算方式 | 对应球检测分数 |
| `bounce` | `None` | `None` | 落台事件分数 |
| `net_hit` | `None` | `None` | 擦网事件分数 |

字段映射应以实际部署的模型实现为准。不同模型的原始分数含义可能不同，未经校准不能直接比较。

### 7.3 没有检测到球

没有检测到球时，也应输出一条观测，其 `ball` 字段如下：

```python
"ball": {
    "visible": False,
    "center_px": None,
    "bbox_xyxy": None,
    "confidence": None,
}
```

不要填上一次的位置，也不要用 `(0, 0)` 表示丢失。轨迹预测由后续追踪模块完成，并明确标记为“预测位置”，避免被误认为真实检测。

### 7.4 事件处理层输出 Event

事件处理层把观测转换为状态机输入，例如：

```python
event = {
    "event_id": "bounce_00042",
    "timestamp_s": 20.567,
    "type": "BOUNCE",
    "side": "A",               # A / B / UNKNOWN
    "position_px": [850, 420],
    "confidence": 0.90,
    "sources": ["ttnet", "tracknet"],
}
```

### 7.5 时间对齐和事件去重

- **连续帧模型必须对应正确的目标帧。** 如果输入三帧、预测中间帧，时间戳就属于中间帧；若输出多个帧的位置，应分别输出多条观测。
- **`event_scores` 是事件候选分数，不是已经确认的事件。** 连续多帧的高落台分数，要经时间峰值提取、几何验证和去重后，才能产生一个 `BOUNCE`。

最终接口关系：

```text
适配器输出 Observation
    → 追踪、事件提取与融合
    → 输出 Event
    → 计分状态机
```

三个模型可以随时切换或组合，而不用改动计分规则。
