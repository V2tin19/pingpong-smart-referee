# 决策与风险记录

**用途**：记录 YOLO 分支**自行拍板**的接口/实现决策，以及这些决策可能带来的后续风险。

**背景**：组长《共用计分状态机方案》是硬性要求，但其中存在若干**未定义点**（详见
`待确认事项.md`）。为不阻塞开发，这些点按**业界最常见做法**先行确定并实现。

1. 让另两条分支知道我们假定了什么（避免联调时才发现不一致）；
2. 一旦组长后续给出不同规定，能快速定位**需要改哪些地方**；
3. 记录触发条件，便于判断何时必须回头重议。

**维护约定**：每条记录含「决策 / 依据 / 影响面 / 风险 / 触发重议条件 / 回滚方式」。
状态为 `生效` 的条目表示已写进代码。

## R-001 `frame_id` 从 0 开始

- **决策**：`FrameObservation.frame_id` 从 0 计数，第 0 帧为视频首帧。
- **依据**：OpenCV `CAP_PROP_POS_FRAMES`、FFmpeg、绝大多数 CV 数据集与标注工具
  均以 0 为起始；组长 §7.1 未规定起始值。
- **影响面**：三分支的事件时间轴对齐；跨模型去重（组长 §4-3）。
- **风险**：若 TTNet/TrackNet 从 1 开始，事件时间轴整体错 1 帧（25fps 下 40ms），
  在 ±0.08s 去重窗口下**恰好处于边界**，可能造成偶发漏融合。
- **触发重议**：联调时发现三家事件计数系统性差 1。
- **回滚方式**：`core/schemas.py` 的 `frame_id` 校验放宽 + 适配器加偏移；
  改动点集中在各适配器的 `_predict_frame` 入口。

## R-002 `timestamp_s` 由视频实际帧率换算

- **决策**：`timestamp_s = frame_id / fps`，`fps` 取自视频文件元数据
  （`cv2.CAP_PROP_FPS`），**不假定 25fps**。
- **依据**：组长 §7.1 明确"被预测帧的视频时间，不是推理完成时间"；
  数据集文档 P015 警告"200Hz 指真值采样率，不代表所提供视频一定是 200 帧/秒"。
- **影响面**：所有时间判据（超时、冷却、去重窗、状态机消抖）。
- **风险**：
  - 若视频元数据 fps 不准（VFR 可变帧率视频），换算出的时间戳会漂移；
  - 组长 §4-1 要求"不使用固定帧数"，一旦时间戳不可靠，该要求无法真正落地。
- **触发重议**：遇到 VFR 视频，或三家在同一视频上算出的时间戳不一致。
- **回滚方式**：改用**逐帧真实 PTS**（`CAP_PROP_POS_MSEC`）而非 `frame_id/fps`。
  适配器接口不变，只换内部换算。

## R-003 事件类型枚举

- **决策**：物理事件固定为 4 类 —— `BOUNCE`（落台）/ `RACKET_HIT`（击球）/
  `NET_TOUCH`（擦网）/ `OUT`（出界）。
  **「回合结束」与「得分方」不进事件枚举**，它们是状态机的状态与输出。
- **依据**：
  - 组长 §7.4 示例为 `BOUNCE`，注释"落台、击球、擦网等"（开放式列举）；
  - 数据集文档 P017 列出我们自录评测集需要标注的内容：
    "落台、击球、出界、回合结束和得分方"——前四项中前三项 + 出界 = 物理事件，
    后两项 = 判罚结果。
- **影响面**：`RefereeEvent.type` 的全部取值；状态机输入契约。
- **风险**：若组长或另两条分支认为"出界"应由状态机从落点推导（而非作为独立事件），
  或认为需要 `LET`（擦网重发）作为事件，枚举需要调整。
- **触发重议**：状态机联调；组长补充事件类型规定。
- **回滚方式**：`core/schemas.py::EventType` 增删枚举值 + 事件层映射。改动局部。

## R-004 `side` 表示画面/球台左右

- **决策**：`side = "A"` 表示画面**左侧**半台，`"B"` 表示右侧；与发球方/接发方无关。
  主客关系由状态机结合发球轮次换算。
- **依据**：组长 §7.4 定义了 `A`/`B`/`UNKNOWN` 但未说明语义；按"物理侧"解释最自然，
  且与单应性变换、球台几何天然一致。
- **影响面**：`RefereeEvent.side`；状态机的左右半台判罚。
- **风险**：若 TTNet 把 `side` 理解为"发球方/接发方"，语义直接冲突，
  且**不会报错**——只会静默判错分。这是本表里最隐蔽的一条。
- **触发重议**：与另两条分支对齐接口时**必须主动确认**（已列入 `待确认事项.md` A5）。
- **回滚方式**：语义变更需三家同步；代码上仅影响 `geometry.side_of()` 与状态机映射。

## R-005 事件去重时间窗 ±0.08s

- **决策**：同一类型事件在 ±0.08s 内视为同一次，聚合为单条 `RefereeEvent`。
- **依据**：组长 §4-3 要求"同一次落台只能产生一个事件"、§7.5 要求"时间峰值提取、
  几何验证和去重"，但未给窗口大小。±0.08s ≈ 25fps 下 ±2 帧，是常见取法。
- **影响面**：多模型融合（组长 §4-3）；单模型下的重复事件抑制。
- **风险**：窗口过小 → 同一次落台被算两次（重复加分）；窗口过大 →
  连续两次真实击球被合并（漏判）。乒乓球高速对拉时两次击球间隔可低至 ~0.2s，
  0.08s 窗口相对安全，但需实测验证。
- **触发重议**：实测出现重复加分或漏判击球。
- **回滚方式**：`TrajectoryEventProcessor` 的窗口常量；单点可调。

## R-006 多候选走带外通道

- **决策**：一帧内的多个检测候选通过 `BaseAdapter.candidates_for(frame_id)` 提供，
  **不写入** `FrameObservation`。
- **依据**：组长 §7.1 是冻结的字段集合；§1/§6 要求"统一观测"，各分支自行扩展会让
  契约退化。
- **影响面**：仅 YOLO 适配器；另两条分支默认返回空列表，无感。
- **风险**：候选不能随观测一起序列化跨进程传递。若将来需要"离线多模型候选级融合"，
  需要另设通道（但该场景更适合走事件层）。
- **触发重议**：需要离线候选级融合时。
- **回滚方式**：删除 `candidates_for` 即可，无残留。

## R-007 目录布局

- **决策**：仓库根目录下 `core/`（契约、基类、几何）+ `adapters/`（各模型适配器）+
  `tests/`。
- **依据**：参考 AI 草稿《工作全貌》§4.1，**非组长硬性要求**。
- **风险**：若组内最终统一到别的布局（例如按分支分目录），需要迁移。
- **回滚方式**：纯文件移动 + 改 import；契约本身与路径无关。

## R-008 状态机判罚细则 —— ⚠️ 高风险，未定

- **现状**：组长 §3 只给出状态序列（等待发球 → 发球进行中 → 对打中 → 回合结束候选 →
  确认得分，旁路人工确认），措辞为"可以先设置"。以下细则**组长文档未规定**：
  - 发球三段校验的具体判定；
  - 擦网重发（LET）的判定与比分处理；
  - 回合终了消抖时长（AI 草稿建议 0.4s，**非硬性**）；
  - 双跳违例判定。
- **风险**：**这是三分支最容易各写一套、导致判分不一致的地方**，
  直接违背组长"不要三套互不相通的计分规则"的核心意图。
- **必须动作**：在实现状态机**之前**与组长及另两条分支统一细则。
- **回滚方式**：细则未定前，状态机只实现骨架（状态迁移 + 接口），判罚阈值参数化。

## R-009 保留文件名嗅探作为 CLI 便利函数

- **决策**：`core/geometry.guess_preset_name()` 仍按文件名猜标定预设，但**仅供命令行/
  基准脚本复现历史结果使用**；适配器与事件层必须接收显式 `TableCalibration`。
- **依据**：兼容 `smart_referee_yolo.py` 的历史行为，保证既有指标可复现。
- **风险**：若有人图省事在正式链路里调用它，会重新引入"换机位就要改代码"的老毛病。
- **回滚方式**：函数已加显著警告注释；必要时可加 deprecation。

## R-010 `OUT` 作为独立事件类型

- **决策**：出界作为独立 `RefereeEvent` 上报，而非仅由状态机从落点推导。
- **依据**：组长 §7.4 为开放式列举（"…等"）；数据集文档 P017 明确自录评测集需标注"出界"。
- **风险**：与 R-003 同源，若组长认为出界应由状态机推导，需调整。
- **回滚方式**：同 R-003。

## R-011 TT3D 真值 200Hz 与视频帧率不一致 —— ⚠️ 高风险，待实现

- **来源**：数据集文档 P015 —— "200 Hz 指真值跟踪的采样率，不代表所提供视频一定是
  200 帧/秒"。
- **风险**：若阶段三用 TT3D 做落点/轨迹验证，**按帧号对齐会错位**；
  必须按**时间戳重采样**对齐。
- **必须动作**：轨迹验证脚本一律以 `timestamp_s` 为对齐基准，禁止用帧序号索引真值。

- **回滚方式**：验证脚本内部实现，不影响契约。

## R-012 `OUT` 的判据：台外落点拐点 —— 一次实测修正

- **决策**：`OUT` 只在**球发生落点拐点（垂直速度由下转上）且落点在球台多边形之外**
  时报出。与 `BOUNCE` 共用同一个拐点检测器，仅按落点位置分流。
- **依据**：**实测数据**。第一版实现用的是"球在下降 + 已在台外"，在
  `test_game_2.avi` 上产生 **18 次 OUT**，而老脚本只有 1 次。原因是正常对拉时
  球经常在台外下降（飞向球员、飞出台面侧方），这根本不是出界。
  改为"台外拐点"后降到 **1 次**，与老脚本一致。
- **影响面**：`TrajectoryEventProcessor._extract_events` 的分流逻辑。
- **风险**：
  - 球**未落地就飞出画面**（长球直接出界）不会被本层捕获 —— 这是**有意为之**，
    符合组长 §4-2"不要把球消失当失分"；该情形应由状态机的
    `RALLY_END_CANDIDATE` + 超时判据处理。
  - `out_margin_px = 25` 是标定误差容差；标定不准时可能把台边球判成出界。
- **触发重议**：状态机接入后，若"出界"判罚与人工标注差异较大。
- **回滚方式**：单点修改 `_extract_events` 中的分流条件。

## R-013 `OUT` 只在"良态区域"判定

- **决策**：`OUT` 要求落点在图像上位于**球台近边之下**（球已落到台面以下），
  即 ``ProcessorParams.out_requires_near_region = True``。
- **依据**：**实测数据**。改为厘米空间判定后，`test_game_2.avi` 上报出 9 次 OUT，
  但其图像 y 坐标全在 **487~575**，而球台近边在 **654**——全部位于球台**远端上方**。
  那片区域透视压缩极严重：距台面顶边仅约 40px 的位置，单应性会算出"台外 85cm"。
  透视把像素噪声放大成了几十厘米的虚假出界。老代码用 `cy > 670` 做同样的限制。
- **影响面**：`TrajectoryEventProcessor._in_out_region`。
- **风险（有意接受的取舍）**：
  - **远端长球（出界但落在台后）不会被本层捕获**。这是刻意的：牺牲远端召回，
    换出界事件的可靠性。该情形由状态机的 `RALLY_END_CANDIDATE` + 超时判据处理，
    与组长 §4-2"不拿弱证据判分"一致。
  - 若将来换成俯视/高位机位（远端不再压缩），应关闭此限制。
- **触发重议**：换机位；或状态机接入后发现长球漏判明显。
- **回滚方式**：`ProcessorParams(out_requires_near_region=False)`，一行参数。

## R-014 显式拒绝 `ball.predicted=true`

- **决策**：解析统一观测时，若 `ball.predicted` 为真，**直接抛错**，而不是静默忽略。
- **背景**：TrackNet 分支交付的 `observation.schema.json` 在 `ball` 里加了一个可选的
  `predicted` 字段（表示 `center_px` 是轨迹推断位置而非模型检出）。他们的参考实现
  并不产生该字段（600 帧样例里 0 行含此键），所以当前无实际数据冲突。
- **依据**：我们的 `from_dict` 只挑自己认识的键，**未知键会被静默丢弃**。若真收到
  `predicted=true`，会把一个轨迹推断位置当成真实检测混进事件层——正是组长 §7.3
  要防的"被误认为真实检测"，而且**不会报错**。静默出错比直接报错危险得多。
- **影响面**：`core/schemas.py::BallObservation.from_dict`。`predicted=false` 或缺省
  仍正常接受，因此与现有数据**完全兼容**。
- **风险**：若组长最终决定采纳 `predicted` 进入契约（见 `待确认事项.md` A9），
  需要改为"接受并标记"而非拒绝。
- **回滚方式**：单点修改 `from_dict`，并在 `BallObservation` 上增加字段。

## R-015 发球判定要求"死球停顿"

- **决策**：只有距上一个事件 **≥ 1.5s**（`MatchRules.serve_min_gap_s`）的第一次击球
  才被当作发球；间隔不足时视为**对打的延续**。
- **依据**：**实测数据**。第一版把"每分重置后的第一次击球"当作发球，于是正常对打中
  "球落在对方半台"被 `SERVE_FAULT` 误判——`test_game_2` 上 12 分里有 **8 分**来自这条。
  本质问题是：**从事件流里分不出"发球"和"对打中的一次击球"**。真实比赛每分之间有
  数秒停顿，对拉中两次击球间隔通常 <1s，用停顿区分是可靠的。
- **影响面**：`core/state_machine.py::_on_racket_hit`、`MatchRules.serve_min_gap_s`。
- **风险**：1.5s 是**假设值**。若视频被剪辑过（分与分之间的停顿被剪掉），发球将
  永远识别不出来，`SERVE_FAULT` 与发球相关的规则全部失效（表现为"发球相关判罚为 0"）。
- **触发重议**：换视频后发球相关判罚恒为 0；或拿到自录数据可测量真实分间间隔。
- **回滚方式**：单参数调整；设为 0 即退回"每次重置后的第一次击球都算发球"。

## R-016 落台判据必须含水平方向守卫

- **决策**：`_is_bounce` 在垂直拐点判据之外，**必须**同时满足"水平速度未反向"。
- **依据**：**实测数据**。球拍击球同样会造成垂直速度反转（球员把球往上打），
  因此只靠垂直拐点分不出落台与击球。实测出现 `RACKET_HIT` 与 `BOUNCE` **同帧双触发**
  （frame 153 / 392），导致状态机里"击球方"与"落台侧"变成同一侧，正常对打被误判成
  `OWN_COURT` 12 次。
- **教训**：老代码里有这条守卫（`v_prev[0] * v_curr[0] >= -1.0`），本模块重写时遗漏。
  **重写算法时，原有守卫条件必须逐条对照迁移，不能只迁移主判据。**
- **影响面**：`core/trajectory_processor.py::_is_bounce`（已有回归测试）。
- **风险**：极端擦边球若同时伴随轻微水平反向，会被漏判为落台。
- **回滚方式**：删除该守卫（但不建议——会退回 12 次误判）。

## R-017 击球方按"球被击出后的飞行方向"归属

- **决策**：`RACKET_HIT` 事件的 `side` **不再**用检出位置 `side_of(point.x)` 推断，
  改为按击出后的水平速度方向：球往右飞(`vx_curr > 0`) → 击球方在左(A)；反之在右(B)。
- **依据**：**实测数据**。速度反转是在**实际击球之后几帧**才被卡尔曼检出的，
  而球很快（120fps 下约 10px/帧），检出时球已越过球网。实测 `test_2.mp4`：

  ```
  frame 160  RACKET_HIT  A  pos=(882, 461)   ← x=882 距球网(929)仅 47px
  frame 179  BOUNCE      A  pos=(476, 579)   ← 于是被判成"击球方打进自己半台"
  ```

  物理上球员一定把球打向**对方**半台，所以"球往哪飞"才是击球方的可靠判据。
- **效果**：`test_2.mp4` 上 `OWN_COURT` 从 **8 次降到 1 次**，总判罚从 10 次降到 3 次，
  比分从 2:8 变为 **1:2**（30 秒内 3 分，对真实比赛片段是合理量级）。
- **影响面**：`core/trajectory_processor.py::_extract_events`、`_emit(side=...)`（已有回归测试）。
- **风险**：若球被击出后立刻被对方击回（极快对拉），`vx_curr` 可能已再次反向。
  当前有冷却窗与去重保护，极端快节奏下仍可能误判。
- **回滚方式**：`_emit` 不传 `side` 即退回按位置推断。

## R-018 `test2` 预设复用 game2 标定

- **决策**：`CALIBRATION_PRESETS["test2"]` = game2 标定（仅改名字）。
- **依据**：**实测验证**，非假定：
  * 把 game2 的球台多边形套在 `test_2.mp4` 上，台面色像素覆盖率 **99.6~100%**
    （game2 自身也是 99.6%）；
  * 同一视频时刻整帧平均绝对差仅 **7/255**，下半幅（球台/地面）6.7/255。

  标定会错。文件名嗅探仅用于命令行便利，正式链路必须显式传标定。

## R-019 起轨与静止门限：由"每帧位移"改为"速度 + 时间"

- **决策**：把两条**空间门限**从"每帧像素位移"改成与帧率无关的形式：

  | 原（每帧位移） | 现（速度 / 时间） |
  |:---|:---|
  | `confirm_min_px = 3.5` px/帧 | `confirm_min_speed_px_s = 50` px/s |
  | `confirm_max_px = 65` px/帧 | `confirm_max_speed_px_s = 8000` px/s |
  | `static_eps_px = 1.0` px/帧（连续静止） | `static_min_travel_px = 3.0` px / `static_max_s = 0.12` s |

- **依据**：**实测**。此前只把**时间**判据改成了秒（组长 §4-1），但**空间**门限仍是
  "每帧位移"，导致起轨能力仍强依赖帧率。实测扫描（球速 × 帧率）：

  * 帧率**太低** → 快球每帧位移超过上限 → 起不了轨；
  * 帧率**太高** → 慢球每帧位移低于下限 → 起不了轨。

  修复前有 **15/64** 组不可用；修复后 **0/64**（50~8000 px/s × 10~960 fps 全覆盖）。

- **上限取值依据实测球速分布**（三份视频，px/s）：

  | 视频 | p5 | 中位 | p95 | 最大 |
  |:---|:---:|:---:|:---:|:---:|
  | test_game_2 (25fps) | 339 | 408 | 830 | 1602 |
  | test_2 (120fps) | 425 | 2133 | 4734 | **5106** |
  | test_rally (25fps) | 33 | 137 | 1469 | 3318 |

  真实范围约 33~5100 px/s。下限取 50（挡掉静止反光、容得下慢球），
  上限取 8000（约实测最大值的 1.6 倍，对应约 30 m/s 极限扣杀）。

  **注意**：老代码的 `65px/帧 @25fps = 1625 px/s` 只够覆盖 test_game_2 那种慢球，
  照搬会把 test_2 里的快球全部拒掉。

- **影响面**：`core/trajectory_processor.py` 的 `ProcessorParams`、`_try_acquire`、
  `_is_static`（已有回归测试：帧率无关性、快球起轨）。
- **风险**：上限放宽到 8000 px/s 后，起轨阶段对"远处误检"的容忍度变大
  （25fps 下允许单帧跳 320px）。但一旦建立跟踪，后续关联仍受
  `gate_near_px / gate_mid_px` 约束，影响有限。
- **回滚方式**：把两个字段改回每帧位移并恢复旧值即可（不推荐）。

## R-020 状态机把 `side=UNKNOWN` 当"信息缺失"处理

- **决策**：`RefereeEvent.side` 允许 `UNKNOWN`（§7.4 文档承诺"状态机会把 UNKNOWN
  当作信息缺失处理"），状态机兑现该承诺：
  * UNKNOWN 的**击球**：不建立发球归属（server 无从确定）、不更新 `last_hitter`、
    清空 `last_bounce_side`，只把状态从等待带回到对打；
  * UNKNOWN 的**落台**：不参与任何判罚，也不写入 `last_bounce_side`；
  * `_award()` 增加防御校验：胜者只能是 `"A"`/`"B"`，否则当场抛错。
  处理原则：**已知信息不被未知信息覆盖，未知信息绝不参与判罚**。
- **依据**：**实测复现**（合成事件序列）。修复前 UNKNOWN 击球会静默建立
  `server="UNKNOWN"` 并成为 `last_hitter`，随后的落台会**凭空给某一侧加分**；
  对打中 UNKNOWN 击球 + 同侧二跳会触发 `points["UNKNOWN"]` **KeyError 崩溃**。
  我们的 YOLO 事件层从不产生 UNKNOWN（`side_of()` 只返回 A/B），
  但 TTNet / TrackNet 的事件层**允许**填 UNKNOWN——状态机是三分支共用组件，
  必须先在这里守住。
- **影响面**：`core/state_machine.py::_on_racket_hit` / `_on_bounce` / `_award`
  （已有回归测试：4 项 UNKNOWN 语义 + 崩溃路径）。
- **风险**：UNKNOWN 击球会清空击球归属，其后到下一次已知击球之间的落台
  无法判罚（回合终点可能记为死球）。这是"信息不足时不猜"的有意取舍，
  与组长 §4-2 精神一致；本分支事件层不产生 UNKNOWN，实际不影响现有指标。
- **触发重议**：若某分支的事件层开始大量输出 UNKNOWN，应推动其补全判侧，
  而不是在状态机里猜测。
- **回滚方式**：删除 `_on_racket_hit` / `_on_bounce` 开头的 UNKNOWN 分支即可。

## R-021 落台侧归属按球台物理坐标（单应性），不按像素 `net_x`

- **决策**：`BOUNCE` 事件的 `side` 用 `homography.side_of_cm(landing.x_cm)`
  （落点 x_cm 与 137cm 物理球网线比较）判定，不再用像素域的
  `calib.side_of(point.x)`（与 `net_x=929px` 竖直线比较）。
- **依据**：**实测**。透视下图像上的一条竖直线并不对应球台平面上恒定的物理 x：
  game2 标定里 `net_x=929px`，在 y≈549 处 929px 实际映射到 **134cm**（球台左半台）。
  也就是说 930~940px 的近网落点物理上在 A 侧，按像素判会被归成 B——
  进而让状态机把正常对打误判成 OWN_COURT。这与 R-017
  （击球方按飞行方向归属，不按检出位置）是**同一类修正**：
  判"侧"要依据物理，不要依据图像上的近似。
  合法性：落点拐点意味着球就在台面平面上，投影符合 §5。
- **影响面**：`core/trajectory_processor.py::_extract_events` 的 BOUNCE 分支
  （已有回归测试：构造近网落台，断言像素判侧 ≠ 事件 side 且事件 side 与
  物理判侧一致）。`OUT` / `NET_TOUCH` 仍用像素判（前者状态机不消费 side，
  后者的像素窄带判据是刻意设计，见 `_is_net_touch` 文档）。
- **风险**：极小。近网落点（±3cm 内）的判侧才可能变化，且变化方向是
  "更符合物理"。`test_2.mp4` 复测：比分、事件计数、规则贡献与修复前**完全一致**。
- **触发重议**：若组长规定 `side` 必须按像素域判定。
- **回滚方式**：`_emit(BOUNCE, ...)` 不传 `side` 即退回像素判侧。

## R-022 状态机四条"参考门控"（学长 2026-11-04 布置）

- **决策**：在判罚之前加四道门，全部做成 `MatchRules` 可单独开关的机制，
  每道门在 `describe()["gates"]` 留触发计数：
  1. **发球准入**（`enable_serve_admission=True`）：必须见证 **"本方台面落台 →
     对方台面落台"** 序列，回合才升为可判分；准入期间**同侧再弹视为发球前的
     准备动作**（颠球/拍球找手感），重置候选、绝不判 DOUBLE_BOUNCE；序列始终
     无法完成的由超时作废（死球）。发球阶段 SERVE_FAULT / 二跳判分移入旧版
     模式（`enable_serve_admission=False` 才可用）。
  2. **发球前击球校验**（`pre_serve_hit_window_s=1.5`）：准入序列完成（升级）
     时刻，最近一次 `RACKET_HIT` 必须在窗口内——手抛传球、滚球等**没有球拍
     接触**的弹跳序列直接挡下。
  3. **回合内击球要求**（`enable_rally_hit_required=True` + `enable_splice_guard=True`）：
     升级后的回合内**至少一次已知击球**才允许任何判分（发球 ace / 发球二跳家族
     一律放过，宁漏勿误）；**"同侧两弹之间夹一次击球"视为序列误拼**（虚假击球 +
     漏检拼接的典型形态），不计分。
  4. **判分后冷却与默认不判分**（`score_cooldown_s=2.0` + `enable_no_return=False`）：
     判分后进入 `CONFIRM_POINT` 冷却 2s、**忽略全部事件**（捡球/庆祝/反光进不来；
     换发在判分瞬间计算，证据清理推迟到冷却期满）；静默超时与视频结束默认只
     清理证据不判分——`NO_RETURN` 默认值由开启改为关闭。
- **依据**：学长布置 + **Test4 实测**（`docs/test4_evaluation_report.md`）：
  * 帧 828 把发球前第 2 次颠球判成 DOUBLE_BOUNCE，比赛未开先送 0:1（门控 1）；
  * 底噪误检造成大量虚假 RACKET_HIT，"落台→虚假击球→同侧再弹"被误拼成
    OWN_COURT/DOUBLE_BOUNCE（门控 3b）；
  * 每分结束后捡球期间的杂散事件可能立即触发下一轮误判（门控 4 冷却）。
  **修复验证**：test_4 前 12.5s 复放，误判比分 0:1 → **0:0**
  （`serve_prep_resets=1` 正是帧 828 那记颠球被重置吸收），单测 176 项全过。
- **影响面**：`core/state_machine.py`（`_on_racket_hit` / `_on_bounce_serve_admission` /
  `_on_bounce_rally` / `_award` / `tick` / `update`）、`tests/test_state_machine.py`
  （发球阶段测试按门控语义重写 + 新增 4 个门控测试类）、`tests/run_end_to_end.py`
  的 CLI 开关（`--enable-no-return` / `--legacy-serving` / `--no-splice-guard` /
  `--no-rally-hit-required`）。R-015 的"死球停顿"判据退居旧版模式，被门控 1 的
  落台序列验证**取代**（停顿不再承担发球识别，误报源头消失）。
- **风险**：
  * **召回换精度**：发球 ace（接发方从未触球）、真实发球失误不再判分；
    剪辑视频里"切进对打中段"的回合无法升级、不给分——与"第一版求准不求全"的
    取舍一致，全部可用开关消融恢复。
  * 门控 3b 会拦下部分**真实**的 OWN_COURT（它天然呈"同侧两弹夹击球"形态）；
    需要 OWN_COURT 敏感度时关 `enable_splice_guard`。
  * 门控 2 的 1.5s 窗口按真实发球节奏（击球→对方落台 0.5~1.1s）留有余量，
    极慢高抛发球可能被挡（可调参）。
- **触发重议**：自录带真值评测显示误杀率过高；或组长/学长给出不同门控参数。
- **回滚方式**：四个开关全部关回旧值
  （`enable_serve_admission=False, enable_rally_hit_required=False,
  enable_splice_guard=False, score_cooldown_s=0, enable_no_return=True`）
  即恢复 2026-10-26 版行为。

## R-023 状态机入口按 `event_id` 幂等

- **决策**：`update()` 入口对重复 `event_id` 静默忽略并计数
  （`gates["duplicate_event_ids_ignored"]`），不重复判分；刻意放在时间单调校验

- **依据**：学长转发的《YOLO 仓库状态机修改方案》（AI 起草，按参考提案对待，

  采纳项：小而实、零判罚行为变化。
- **影响面**：`core/state_machine.py::update/reset`、新增 5 项单测

- **回滚方式**：删除 `update()` 入口的去重块即可。

## R-024 感知降噪 P1：关联速度硬截断 + 球台地板掩码（conf 维持 0.18）

- **决策**：Test4 报告 §四.1 三项降噪中，两项代码级落地、一项维持现状：
  1. **P1-3 位移硬截断 → 关联速度守卫**（`ProcessorParams.max_assoc_speed_px_s=9000`，默认开）：
     已跟踪目标与新观测的**隐含速度**（位移 / 距上一真实观测的时间差）超过上界即断轨重捕，
     绝不把瞬移喂进卡尔曼。用**速度**而非报告原话的"px/帧"，延续 R-019 的帧率无关原则；
     上界 9000 = 官方真值实测最大球速 7023 px/s（test_4 @120fps）的 1.28 倍，构造上零召回损失。
     守卫挡的是"能通过 90px 候选门、但物理上不可能是同一个球"的检测瞬移——
     25fps 下隐含速度天然低于此值，守卫自动失效（有单测）。
  2. **P1-2 球台 ROI 掩码**（`YOLOAdapter(floor_margin_px=…)`，默认关；入口脚本
     `--reject-floor`）：检出中心低于 `球台近边 y + margin`（分辨率等比缩放）即物理丢弃。
     依据真值实测：test_4 真球全程不低于近边以下 16px，margin=30 零召回损失。
  3. **P1-1 conf 门限维持 0.18**：实测 0.35 只能杀 42.3% 的 FP（1935/4574），
     却要误杀 8.7% 的真球候选（21/241）——本片误检主体是 conf≥0.35 的台面区
     持久热点（57.7%），提门限收益/代价比不划算，交给 P1-3 + 状态机门控兜底。
- **依据**（`tools/analyze_gt_envelope.py` + `tools/analyze_fp_locations.py`，均本轮新增）：
  * 真值包络：真球最低 y=766（近边 750 以下仅 5/504 帧）、最大 7023 px/s；
  * 误检位置（隔帧 3001 帧实测）：FP 4574 个中**仅 0.3% 在地板区**——
    **修正了 Test4 报告问题一"地板反光"的机理描述**：本片误检主体是台面区
    强置信度热点（球台远边白线亮点、台外背景高光、缓慢漂移物）；
  * bbox 实测：TP 与 FP 尺寸/长宽比**完全同分布**（均 ~19px 方形），几何后过滤无解——
    剩余 57.7% 的强误检**只能靠模型重训**（需把热点位置做难例挖掘加入负样本）。
- **影响面**：`core/trajectory_processor.py`（`max_assoc_speed_px_s` + `_advance` 守卫 +
  `stats["rejected_assoc_jumps"]`）、`adapters/yolo_adapter.py`（`floor_margin_px` +
  `_reject_below_table` + `floor_rejected_count`）、`run_referee.py` / `tests/run_end_to_end.py`
  （`--reject-floor`）。单测 +13 项（总 183→196）。
- **风险**：
  * 速度守卫的 9000 上界来自 test_4/test_2 实测；若未来视频出现更快真球（如更近机位），
    会误断——表现 为 `rejected_assoc_jumps` 偏高、起轨频繁失败，可调参或置 0 关闭；
  * 地板掩码会同时丢弃"长球落地板"的反弹证据（OUT 事件的一个来源）——本片实测
    真球不落可见地板，其他机位启用前应先跑 `analyze_gt_envelope.py` 确认。
- **触发重议**：换机位/换权重后 `rejected_assoc_jumps` 或 `floor_rejected` 异常偏高；
  或重训后热点误检下降，重新评估 conf 门限。
- **回滚方式**：`ProcessorParams(max_assoc_speed_px_s=0)` 恢复旧关联行为；
  不传 `floor_margin_px` / 不加 `--reject-floor` 即掩码关闭（默认即关）。

## R-025 确认帧后候选选择恢复距离门控（瞬移劫持的入口修复）

- **决策**：两帧确认（`_try_acquire`）成功建立跟踪时，把 `_last_prediction`
  钉在确认位置——修复此前确认帧的 `predict()` 发生在卡尔曼初始化**之前**、
  `_last_prediction` 为 `None`，导致**下一帧**候选选择误入"未跟踪"分支的 bug。
- **依据**（test_4 帧 4558~4560 逐帧取证，`_diag` 复放）：
  * 帧 4558/4559 两帧确认成功跟住真球 (1526,402)→(1528,395)；
  * 帧 4560 候选：真球延续 (1531,390) conf 0.32 vs 台面白线热点 (1175,623)
    conf 0.38。旧代码距离盲选、只看置信度 → **热点胜出**，一步瞬移
    590px/帧（隐含 50523 px/s）—— Test4 报告"问题一"的瞬移正是从此进入；
  * 该劫持随后 wobbling 出的**伪 RACKET_HIT（帧4562）与伪 BOUNCE（帧4571）**
    曾被旧管线用作发球准入证据，进而判出帧 4892 的一分——即旧版 1:1 中的
    第二分**骑在被污染的证据链上**。修复后该分按"宁漏勿误"如实转为死球。
- **影响面**：`core/trajectory_processor.py::_try_acquire`（3 行）；
  回归测试 2 项（`TestSelectionAfterConfirmation`：远高置信候选不得劫持 +
  预测参考等于确认位置），总单测 196→198 项。
- **与 R-024 守卫的关系**：本修复在**源头**（候选选择）挡住跨门瞬移，
  R-024 的关联速度守卫退居**第二道防线**（挡门内 67~90px/帧 的物理不可能位移）。
  修复后帧 4560 的劫持不再发生（窗口复放零触发），全片守卫仅余 1 次触发
  （其他位置的门内瞬移拦截；最终 0:1 与窗口取证预期一致，未影响判分）。
- **风险**：`_on_missing` 在确认帧后若立即漏检，现可用确认位置外推
  （旧代码因 `_last_prediction is None` 不外推）——行为更连续，无召回损失。
- **触发重议**：无（缺陷修复，非取舍）。
- **回滚方式**：删除 `_try_acquire` 中 `_last_prediction` 赋值一行即回到旧行为
  （不建议，会重开瞬移入口）。
